# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

AES-driven, IDO-layer data replication for Infor CloudSuite Industrial (Syteline), built on the Mongoose framework. Administrators define replication rules (which IDO and which events), credentials for external targets, and field-level maps and transformations. When a record changes, the rule's IDO extension class loads the record, remaps it, and pushes it to the target. Working targets are Azure Event Hubs (including Fabric Eventstreams through a custom endpoint) and the Salesforce REST API. The project is pre-beta.

Nothing here runs locally and there is no test suite. Changes are deployed into Syteline through Mongoose tooling.

This is an MIT-licensed, open-source project meant for any company's Syteline instance. Don't hard-code company-specific values (URLs, names, sites). Make them settings on a credential or rule instead.

## Naming

Everything uses the `AIR` prefix: tables `ue_AIR_idorepl_*_mst`, IDOs `ue_AIR_*` on IDO server `ue_AIR`, forms `ue_AIR_*`, assemblies `ue_AIR_*_ECA`.

## Mongoose facts that are easy to get wrong

Each of these has caused a real bug in this repo or was found by testing in Syteline. Check this list before relying on memory, and add to it whenever a wrong assumption about Mongoose or Syteline is found and corrected.

- **Record cap: 0 means no cap. -1 means the default cap of 200.** This holds for `LoadCollection` requests, for `SytelineInternalAPI.LoadRecords`, and for `RECORDCAP( )` in a form's List Source or data source. -1 does not mean "unlimited". To load every record, pass 0. In C#, use `SytelineInternalAPI.NoRecordCap` (0) and `SytelineInternalAPI.DefaultRecordCap` (-1), never the bare numbers.
- **A List Source can't be a form variable as a whole.** `V(SomeListSource)` fails with "Unsupported list source format". Only the entries inside `INLINE ENTRIES( )` can come from a variable.
- **A Script list source runs a global script**, not a method of the form's own script.
- **An ItemID goes out of date when its row is updated.** An ItemID holds the row's `RecordDate`, and an update that gives an ItemID uses optimistic locking (`IDOUpdateItem.UseOptimisticLocking` defaults to true), so it is refused when the row has changed since it was loaded. To update the same row twice, load its ItemID again before the second update, as `LoadCurrentLogItemIDs` does in the Rules ECA. This comes from reading the Infor DLLs in `Lib/`, and hasn't been seen fail in Syteline yet.
- **`DateTime.Now` in an extension class is the application server's time, not the site's.** In a hosted environment that is UTC. Syteline stamps `CreateDate` and `RecordDate` in the site's time zone, through the database function `dbo.GetSiteDate(GETDATE())`. A time the code writes to a table, or compares with one of those dates, has to come from `LoadSiteDateTime` in the Rules ECA, which reads the derived property `CurrentSiteDateTime` on `ue_AIR_IDOReplicationRules` (expression `dbo.GetSiteDate(GETDATE())`) and falls back, when it can't, to `DateTime.Now + IDORuntime.ServerTimeOffset` (the runtime's own offset, worked out once per process, so it can be an hour out after a daylight saving change) and then to the server's time. A background task says so in its messages. The replication log's `LastAttemptDate` was written with `DateTime.Now` and showed five hours after the row's `CreateDate`.
- **A property bound to a column that doesn't exist makes every save to that IDO fail.** Add the column and refresh the table's view before importing an IDO that binds it, and say so in the upgrade steps.
- **A property can be read-only through its property class, and a read-only property's writes are dropped without an error, even from an extension class.** An empty `<PropertyAttributes />` in the export doesn't mean writable. The log's `RecordRowPointer` uses the `RowPointer` class, which is read-only, so every value the Rules ECA wrote to it was dropped and the column stayed empty in every row until `<IsReadOnly>0</IsReadOnly>` was set on the property. Exports of other IDOs (in `infor-customizations`) carry that same override, but whether the import applies it over the class still has to be checked in Syteline after import. Check a property in the running IDO (its flags, or a row written to it) before relying on a write to it.
- **A `RowPointerType` column left out of an insert gets a new random GUID, not NULL.** The type's default is a new GUID, and `SytelineInternalAPI.BuildInsertItem` leaves out every null value, so a null in its dictionary doesn't write NULL: the column gets its default. Once the log's `RecordRowPointer` became writable, every log row with no record got a random record row pointer (seen in a cloud sandbox), which Resend Errors would take for a deleted record. To write NULL, add the property to the update item yourself with a null value and `Modified` true, as `SetRecordRowPointer` in the Rules ECA does. Per the DLLs in `Lib/`, `IDOValueType.SetValue(null)` stores the null marker, and `CommandBuilder.CreateInsertSqlCommand` writes a modified null property as `DBNull`, except a property bound to the table's own `RowPointer` column, which it leaves out so the column gets its default.
- **In `IdoOnUpdateCollection` and `IdoPostUpdateCollection`, an event action can't see which records are being saved.** Their context (`EventSystemUpdateCollectionContext` in the DLLs) returns nothing for `P()` and no rows, and each fires once per `UpdateCollection` request, around the item events: `IdoOnUpdateCollection`, then per record `IdoOnItem*`, the save and `IdoPostItem*`, then `IdoPostUpdateCollection`. A form's multi-row save and a REST insert of several records were each one request, and each record was finished, events included, before the next started. Seen in a cloud sandbox with the [Trigger Diagnostics](wiki/Trigger-Diagnostics.md#results) tests. Per the DLLs, a request with `TxnScope` `Item` is split into one request per record (not tested).
- **In an item event, `P()` sees only the properties the caller sent for that record.** Seen in a cloud sandbox: a form sends `RowPointer` on updates and deletes, and on an insert the runtime fills it in by `IdoPostItemInsert`, so the replication trigger's `RowPointer = '<P("RowPointer")>'` filter works for form saves. A REST caller that names records by key sends only the keys, and one that names them by ItemId sends nothing the event can read: `P("_ItemId")` was blank in every test where the ItemID was the change's own `ItemId`. A REST update that sends a property named `_ItemId` (the change's `ItemId` blank, the keys unmodified) went through, seen once on `SLCustomers` with the keys sent too, so most likely matched by the keys, even though the value wasn't an ItemID: `IdoOnItemUpdate` saw the keys and the value as sent, and `IdoPostItemUpdate` saw the row's real ItemID, which holds both base tables' RowPointers (`cus.ID=[...]`, `adr.ID=[...]` on `SLCustomers`). The same value in the change's own `ItemId` field fails the save with "Update request must include the _ItemId property, or the RecordDate and RowPointer properties." after `IdoOnItemUpdate` ([F8](wiki/Trigger-Diagnostics.md#results-of-the-last-tests)). A REST insert didn't get its RowPointer back on `IdoPostItemInsert` even with `refresh=true`. An extension class saving through `this.Context.Commands.UpdateCollection` behaved the same as a REST caller, insert included, even with `RefreshAfterUpdate` set. So the replication triggers miss REST and extension-class inserts, and their updates and deletes that don't include `RowPointer`, which are logged as `Skipped` with a blank filter. ION callers haven't been tested.
- **An event handler's Ignore Failure setting decides whether its writes roll back with the save.** Seen in a cloud sandbox on synchronous `IdoPostItemInsert` handlers in a failing REST insert: with Ignore Failure on, what the handler wrote stayed; with it off, its writes rolled back with the save. The same was seen on synchronous `IdoOnUpdateCollection` handlers in the doorbell test, and with Ignore Failure off on every handler in failing REST inserts, updates and deletes: nothing from `IdoOnUpdateCollection` or the earlier records' item events stayed (for updates and deletes, that those events fired is inferred from the per-record order; [F1](wiki/Trigger-Diagnostics.md#results-of-the-last-tests)). A failed save doesn't reach `IdoPostUpdateCollection`, so that event can't be checked this way. Transactional handlers weren't tested. The replication triggers have it off. `System.Transactions.Transaction.Current` is empty inside a handler's method either way. A REST update or delete by a key that doesn't exist fails the save ("record has been deleted or modified by another user").
- **Right after an assembly upload, a save can fail even through a handler with Ignore Failure on.** Seen once in a cloud sandbox: a REST save failed with `Extension class for ue_AIR_IDOReplicationRules IDO not found`, raised by an `IdoOnUpdateCollection` handler with Ignore Failure on, and the same save worked a few minutes later (Refresh Form Metadata may have been run in between). The cause is unknown. Ignore Failure does take effect on `IdoOnUpdateCollection` (the doorbell test), so the open question is whether it covers an extension class that can't be loaded. The replication triggers have Ignore Failure off, so a save to an IDO with active replication triggers can fail the same way.
- **A background task submitted by an event handler with Ignore Failure off starts only after the save commits, and didn't start when the save failed.** Seen in a cloud sandbox with the doorbell test ([Trigger Diagnostics](wiki/Trigger-Diagnostics.md#doorbell-results)): a synchronous `IdoOnUpdateCollection` handler submitted a task through `BGTaskDefinitions.BGTaskSubmit2`. Task Manager started it 0.4 to 3.9 seconds after the save's last event, even when it was submitted 45 seconds before, and one save that failed left no task. Its code ran about 1 to 6 seconds after the save's last event (two clocks), and the submission cost the save 49 to 322 ms. A handler with Ignore Failure on most likely submits outside the save (not tested). `BG~TASKID~` in the task's parameters is replaced, and a running task is listed in `ActiveBGTasks`.
- **A queued background task shows in `ActiveBGTasks` as `READY` with no `StartDate`, and a load of `ActiveBGTasks` inside a save sees only committed submissions.** Seen in a cloud sandbox with the burst tests: a save's look never listed a task another save had submitted but not yet committed, and didn't wait for it (B3). With the task definition's **Max Concurrent** at 1, Task Manager ran one copy at a time across every task server (B2, B3), and ran committed tasks while an uncommitted one waited (B3).
- **A scheduled background task shows in `ActiveBGTasks` as `WAITING` with no `StartDate` until it starts, not `READY`.** Seen once, read-only, on a cloud sandbox: all 133 rows were `WAITING`. Whether a task passes through `READY` between being due and starting wasn't seen.
- **A REST load reads rows a save hasn't committed yet.** Seen in a cloud sandbox ([F3](wiki/Trigger-Diagnostics.md#results-of-the-last-tests)): while a 300-record REST insert ran, loads of its log rows from another window returned more of them each time, in 240 to 500 ms, without waiting. Per the DLLs in `Lib/`, a load's `ReadMode` (`LoadCollectionRequestData.ReadMode`) is `Default`, `ReadCommitted` or `ReadUncommitted`, and `Default` follows the site's process default `CollectionReadMode`, reading uncommitted when it is `UNCOMMITTED` (most likely the case in that sandbox; not read to confirm) and committed otherwise. A REST load passes none. `SytelineInternalAPI.LoadRecords` asks for `ReadCommitted`. A load with `ReadCommitted` skipped a running insert's new rows, in about 200 ms without waiting, and returned them once the save committed (F3b, seen once; that the database uses read committed snapshot is inferred, not checked, and if so a row a running save updates or deletes would read as its committed version; not tested). Code that must not act on uncommitted data has to load with `ReadCommitted`.
- **Children saved as a nested update of their parent fire no events on the child IDO.** Seen once in a cloud sandbox ([F7](wiki/Trigger-Diagnostics.md#results-of-the-last-tests)): an extension class inserted an order header (`CoNum` `S?`) with its lines nested under it in one `UpdateCollection`. `SLCos` fired its usual events (`IdoOnItemInsert` saw `S?`, `IdoPostItemInsert` the assigned number); `SLCoitems`, with ten active handlers, fired none, and the lines' `RecordDate` (last change; the line IDO has no `CreateDate`) was about 3 seconds after the header's `IdoPostUpdateCollection`. Whether the nested save went through the `SLCoitems` IDO wasn't checked. So no trigger on the child IDO captures them. The header and lines commit together (a failing line rolled the header back in an earlier test of the same method).
- **A handler that writes one log row cost about 90 ms per record.** Seen once each way in a cloud sandbox ([F4](wiki/Trigger-Diagnostics.md#results-of-the-last-tests)): a 100-record REST insert took 36.6 s with two row-writing diagnostic handlers per record and 18.4 s without them.
- **On `SLLedgers`, a filter on `RecordDate` behaved like a full table scan.** Seen in a cloud sandbox: a poll by `RecordDate` took about 2 seconds warm and 9.2 seconds on its first run, against 0.25 seconds on the key (the [polling cost test](wiki/Trigger-Diagnostics.md#polling-results); inferred from timing, the table's row count wasn't recorded). On `SLCos`, `SLCoitems` and `SLCustomers` (`RecordDate` and `AdrRecordDate`) a date filter for the last 5 minutes cost about what a key load did, medians of 260 to 917 ms with slowest loads up to 5 seconds, but the sandbox's table sizes weren't recorded and a production table may be larger ([F5](wiki/Trigger-Diagnostics.md#results-of-the-last-tests)). The project's decision: no indexes on standard tables, because an Infor update could lose them and an administrator shouldn't need database work.
- **Deleting a parent record removes its children without any event on the child IDO, but the parent's `IdoOnItemDelete` can still load them.** Seen in a cloud sandbox: deleting an order header in Customer Orders removed its line, and `SLCoitems` fired nothing (the [cascade delete test](wiki/Trigger-Diagnostics.md#the-cascade-delete-test)). A handler on the header's `IdoOnItemDelete` that ran a rule on `SLCoitems` by `CoNum` loaded and logged every line, for two orders ([F6](wiki/Trigger-Diagnostics.md#results-of-the-last-tests)). In the same test a key Syteline assigns during an insert (the order number, `TBD` until then) was only known by `IdoPostItemInsert`, and each line save was followed by an update of the order header that sent nothing the trigger could read.
- **Check-in and the IDO Import Wizard write an IDO's live version without any event on `IdoCollections`.** Seen once in a cloud sandbox ([IDO definition test](wiki/Trigger-Diagnostics.md#the-ido-definition-test)): the New IDO wizard's create fired insert events (keys `CollectionName` and `DevelopmentFlag=1`, no RowPointer) and a delete in the IDOs form fired delete events, but check-in, checkout and an import fired none. Editing a checked-out IDO wasn't tried. **Replace** was disabled on the checked-out IDO in the IDOs form; an import has changed it in earlier testing. The dates on an `IdoCollections` row looked like UTC.
- **Each runtime app domain works out the replace chains once, when its IDO metadata cache reads the list of IDOs.** Per the DLLs in `Lib/` (not tested): the list comes from `Collections`, checked-out versions included, and each base gets one replacer, the top of its chain (`IDOVersionInfoMap.ResolveInheritance`). A save to the base loads that replacer and every IDO it inherits from, with their extension classes. The list is read again when the metadata cache is discarded (most likely what **Refresh Form Metadata** sends) or the app domain is replaced (after 10 idle minutes, or a restart), so a server can keep an old chain for a while. A replacer that existed as a checked-out version when the list was read goes live at check-in without that. When two IDOs replace the same base, the one read last wins, and the query has no `ORDER BY`.
- **Syteline's SQL replication framework doesn't hold changes in its queue for the rule's interval.** Seen once in a cloud sandbox ([SQL replication test](wiki/Trigger-Diagnostics.md#the-sql-replication-test)), with the IDO XML transfer type and a rule set to **Days** with a start date in the future: the SQL trigger's row in `ReplicatedRows3s` was taken within seconds by the `Replicator`, which tried to send it as an IDO `UpdateCollection` on `TABLE!<table>` (the whole row for an insert, the key columns with `UseKeys="Y"` for a delete). Other interval types weren't tried. With the Data Lake transfer type nothing appeared in the tables checked. The first save of the IDO XML run was held up by about 15 seconds (cause unknown). So replication can't read its changes from that queue.
- **Regenerate Replication Triggers has no choice of category or table, and production's log shows lock timeouts and deadlocks.** Seen on the Replication Management form and in its **View Logs** (`TriggerLogMessages`) in production, on three days, on tables such as `coitem_mst` and `item_mst`. Whether a regenerate with **Regenerate All Triggers** cleared rebuilds every rule's triggers wasn't checked.
- **Don't count on an asynchronous event handler running.** In a cloud sandbox, an asynchronous `IdoPostUpdateCollection` handler never ran, and nothing for it was found in `EventQueues`. The cause wasn't found.
- **Saves are spread across several application servers, each with its own app domain.** In a cloud sandbox, saves ran on at least five servers. Static values in an extension class last only as long as that server's app domain, so an in-memory cache (a token, the rules) can't be relied on between saves. `Process.GetCurrentProcess()` throws a `SecurityException` in the cloud.

## Layout

- `dist/` holds the install package. The numbered folders are the install order:
  1. `1 - SQL (Paste Rows Append)/`: `SQL Tables.csv` and `SQL Columns.csv`, pasted as appended rows into Syteline's SQL Tables/Columns forms to create the five `_mst` tables. Each table also gets a view of the same name without `_mst`, and that view is what the IDO binds as its table.
  2. `2 - IDOs and Extension Classes (IDO Import Wizard)/IDOs and Extension Classes.xml`: an `<ObjectStudioExport>` with the IDOs. The `<CustomAssemblies>` section at the end embeds both compiled extension class DLLs as base64 (`<AssemblyImage>`), so this file changes whenever an assembly is re-uploaded. Never edit those images by hand.
     - `ue_AIR_IDOReplicationRules` binds `ue_AIR_IDOReplicationRules_ECA` and exposes `ue_ReplicateRecordToExternalSystems`, the custom-load `ue_LoadOutputPreview`, `ue_RetryFailedReplications` and `ue_ResendReplications`, plus the test-only `ue_LogTriggerEvent`, `ue_DiagUpdateCollection`, `ue_DiagRingDoorbell`, `ue_DiagDoorbellTask` and `ue_DiagTimeLoad` (see Diagnostics below).
     - `ue_AIR_IDOReplicationConfigs` extends the standard `IdoCollections` IDO (no table of its own, one row per IDO collection). It binds `ue_AIR_IDOReplicationConfig_ECA` and exposes `ue_UpdateAESTriggers`.
     - `ue_AIR_IDOReplicationCredentials`, `ue_AIR_IDOReplicationMapFields`, `ue_AIR_IDOReplicationMapFieldSources`, `ue_AIR_IDOReplicationLogs` and `ue_AIR_EventHandlers` have no extension class.
     - `ue_AIR_IDOReplicationLogs` (table `ue_AIR_idorepl_log_mst`) is the replication log: one row per record per rule, with the source and the operation (see Source and operation below), the name of the credential the rule used (`credential_name`, a snapshot copied into the row so it survives changes to the rule or credential, written as `(none)` when there isn't one because the column is required), the `RowPointer` of the record that was replicated (`record_row_pointer`, property `RecordRowPointer`, named for the record because `source` on this table means what started the run, nullable, loaded with the rule's properties and never sent to the target), the payload as sent (JSON, up to 4,000 characters), the status (`Succeeded`, `Failed`, `Skipped`), the error, and `retries_remaining` (default 3) for the retry task. `WriteReplicationLog` in the Rules ECA writes it at the end of every run: trigger runs (`BGTaskNum` -1) log every record, and background task runs log every record when they loaded 100 or fewer. Above that they log failed records, records with a warning, and records that have a `Failed` row, with or without retries left (`LoadRecordIDsAwaitingRetry`, read by `BuildOutcome`), so the retry task sees that the record was replicated again. `BuildOutcome` is the one place that decides whether a record is logged. A rule that failed before its records were remapped gets one row without a payload. A trigger run whose filter matches no record writes one `Skipped` row per rule (`BuildNoRecordRuleResult`), with no record ID and no payload, whose message shows the filter the trigger passed, because a trigger run has no task messages and would otherwise leave no trace. A trigger run whose filter is `RowPointer = ''` (`IsBlankRowPointerFilter`) isn't loaded at all and gets the same row, because comparing a uniqueidentifier column with `''` is most likely a SQL error, not an empty result. A trigger's filter is `RowPointer = '<P("RowPointer")>'`. In an item event `P()` reads only the properties sent in that save for that record, so a save that doesn't send `RowPointer`, which includes every REST insert, gives a blank filter (see the Mongoose facts above), and these rows record it. Only a failed row with a stored payload gets retries; a payload over 4,000 characters isn't stored. A row's record ID is blank when the rule has no ID field (`Option02`). Such a row is still retried, on purpose, although the retry task can't tell whether newer data was sent since. `ue_RetryFailedReplications(BGTaskNum, purgeAfterDays = 90)`, run as a scheduled background task, first marks `Skipped` any `Failed` row whose record the same rule replicated again later (so old data never overwrites newer data or re-creates a deleted record), then resends up to 500 `Failed` rows with retries left from their stored payloads (oldest first, grouped by IDO, rule and operation, through the same `SendRule`), updates each row, and then deletes `Succeeded` and `Skipped` rows older than `purgeAfterDays` (0 turns the purge off). Rows for an inactive or deleted rule are left alone. `Failed` rows are never purged.
  3. `3 - Mongoose Objects (FormSync)/*.XML`: FormSync exports of the forms (`ue_AIR_IDOReplicationRules`, `ue_AIR_IDOReplicationCredentials`, `ue_AIR_IDOReplicationConfigs`, `ue_AIR_IDOReplicationLogs`, `ue_AIR_IDOReplicationResend`, `ue_AIR_ImportJob`, `ue_AIR_JobFileInputWindow`) plus `Strings.XML`. Form scripts are embedded as `<ScriptLine>` elements. A component's `<Flags>` is a bit mask of `Mongoose.WinStudio.Enums.ComponentFlags` in `Lib/WSEnums.dll`, which holds the designer's dynamic settings: for example `NO_FILTER_IN_PLACE` is 4096, `READ_ONLY_FOR_EXISTING` is 8192 and `READ_ONLY_FOR_NEW` is 16384. Prefer those flags to script for enabling and read-only behavior. The designer's **Component Class** and **Component Class Parameters** (under Inheritance) are exported together as `<DefaultFrom>Class(Parameters)</DefaultFrom>`, for example `UserDefinedType(IDOReplicationTargetType)`. When you describe a form setting to the user, use the designer's name for it.

  These files come from Mongoose export tools. Edit them minimally and keep the exporter's formatting: 3-space indentation, element order, and any UTF-8 BOM.

  When you hand-edit an IDO in the IDO export, also bump that IDO's `<RevisionNo>` by 1 and set its `<RevisionDate>` to the current local (Eastern) time in the same format, for example `2026-11-13T13:28:05`. Otherwise the IDO Import Wizard may not treat it as changed. The new date must also be later than the one already there: Syteline has stamped a revision date about two hours ahead of Eastern time (15:36 on an export made before 14:02 Eastern), so if the date already there is later than now, use a time just after it. After importing, use **Refresh Form Metadata** to clear the IDO cache. After changing an extension class method's signature, use **Resync Parameters** on the IDO method, which reads the parameters from the uploaded DLL, instead of editing them by hand.
- `tools/Test-AIRTriggers.ps1` is a PowerShell test script, not part of the install package. It saves test records through the Mongoose REST API or through `ue_DiagUpdateCollection`, sets up the diagnostic triggers, and times read-only polls (`-Action TimeLoad`, through REST or, with `-ReadMode`, through `ue_DiagTimeLoad`). Its setup and removal stop with an error when the method returns anything but 0. Its sign-in, `ido/load` and `ido/update` calls follow Infor's docs and the owner's `functionaldevices-cis/syteline-api-examples` repository: through the ION API (`-IonApiFile`, the usual way to reach a cloud tenant), a token from the `.ionapi` file's `pu` + `ot` with `grant_type=password`, sent as `Bearer <token>`, and the base URL `iu/ti/CSI`; directly, `GET .../ido/token/{config}` with `username` and `password` headers. `.ionapi` files hold secrets and are gitignored. Its `ido/invoke` call, with the parameters as a JSON array, isn't confirmed by either. See Diagnostics below.
- `wiki/` holds the source for the GitHub wiki (administrator and developer documentation). `.github/workflows/publish-wiki.yml` mirrors it to the wiki when a change to `wiki/` reaches `main`, so edit the pages here, not in the wiki's web editor. A file's name is its page name, pages link to each other by name without `.md`, and `_Sidebar.md` is the navigation. `Replication-Redesign-AES-Plan.md` is a proposed redesign of replication built on AES event handlers, not yet built. Another option, extension class code on IDOs that extend the replicated ones, is still to be explored. `Replication-Redesign-Comparison.md` compares the two, rules out a third (Syteline's SQL replication triggers), and recommends building the AES plan first.
- `src/IDO Extension Class Custom Assemblies/` holds two .NET Framework 4.8 C# class library solutions. They reference Infor DLLs from the sibling `Lib/` folder (`..\..\Lib\*.dll` HintPaths) and use NuGet `Newtonsoft.Json` and `System.ValueTuple` via `packages.config`. The language version is the .NET Framework default (C# 7.3), so avoid newer syntax such as collection expressions (`[]`), target-typed `new()`, `??=`, nullable annotations and file-scoped namespaces.
  - `ue_AIR_IDOReplicationRules_ECA` replicates data. Its IDO methods are `ue_ReplicateRecordToExternalSystems` (the entry point), `ue_LoadOutputPreview`, `ue_RetryFailedReplications` (the retry background task) and `ue_ResendReplications` (the manual resend background task), plus the test-only `ue_LogTriggerEvent`, `ue_DiagUpdateCollection`, `ue_DiagRingDoorbell`, `ue_DiagDoorbellTask` and `ue_DiagTimeLoad` in `Diagnostics.cs`. `ue_ParseSavedMap` exists in the class but is not exposed by the IDO yet.
  - `ue_AIR_IDOReplicationConfig_ECA` manages triggers. `ue_UpdateAESTriggers(idoName, action, ref results)` takes `SetupTriggers`, `RemoveTriggers`, `FixTriggers`, `ActivateAllTriggers` or `DeactivateAllTriggers`, called from the Configs form, and `SetupDiagnosticTriggers`, `SetupStrictDiagnosticTriggers` or `RemoveDiagnosticTriggers`, which no form calls (the REST test script does; see Diagnostics below). Setup creates `EventHandlers` (description `ue_AIR_ReplicationTrigger`) for insert, update and delete on the target IDO, with `EventActions` that call the Rules IDO's replication method with `PARMS(-1, <RowPointer filter>, <IDO name>, 1, "", <operation>)`, where the operation is `Insert`, `Update` or `Delete` for that event. It inserts and then deletes a temporary `CustomAIR` handler to work around a sequencing bug when inserting several handlers at once. Two derived properties compare each action's `Parameters` string exactly, so any change to that string in `SetupTriggers` (or to `OperationForEvent`) must also be made in both expressions, and existing triggers need **Fix Triggers**:
    - `ue_AIR_IDOReplicationConfigs.ue_EventHandlersAreSetup`, one comparison per event. It drives the Setup/Broken status on the Configs form.
    - `ue_AIR_EventHandlers.ue_IsSetup`, one comparison that picks the operation from the handler's `EventName`.

    `SetupTriggers` creates the handlers inactive. `FixTriggers` reads which handlers are active, removes and re-creates them all, and activates the ones that were active before, so fixing triggers never turns replication off. The method isn't transactional, so a failure partway through `FixTriggers` is thrown with a message that says what was done and what to click next. `ue_UpdateAESTriggers` returns 0 when the action worked and 1 when it didn't, with a message that says what it did in `results`.

    The Configs form reads two status properties on `ue_AIR_IDOReplicationConfigs`. `ue_EventHandlersStatus` (`Not Setup`, `Setup`, `Broken`) decides which buttons show, through each button's `VISIBLEWHEN`, and a hidden grid column (`ue_EventHandlersStatusGridCol`) keeps it loaded. `ue_EventHandlersStatusDetail` (`Not Setup`, `Active`, `Inactive`, `Partly Active`, `Broken`) is the status the form displays (in the detail area and as a grid column), and it counts the active handlers in the `EventHandler` table (column `Active`). Don't change the values of `ue_EventHandlersStatus` without changing the buttons.
  - **`Helpers/` and `Models/` are duplicated in both projects and are identical except for the namespace.** When you change a helper or model in one project, apply the same change to the other. Keep the two assemblies separate. The plan is to move the helpers into a separate shared extension class assembly later, not to merge these two.

## How replication works (Rules ECA)

Replication runs inside the user's save, so it must never throw out of the trigger and block that save. Every error is caught, turned into a `ReplicationRuleResult` or log row, and the transaction commits. Keep that true in new code paths. A trigger run (`BGTaskNum` -1) always returns 0. A background task run has no save to protect, so it returns 16 when a rule fails or nothing could be sent, which shows the task as failed, and writes the reason to the task's messages. A background run that names a rule runs it even when it is inactive, so the Rules form's Test tab (which passes `P(RuleNum)`) can test a rule before it is switched on. The delete trigger (`IdoOnItemDelete`) runs before the row is removed, so the record can still be loaded.

Source and operation. Every run has both, and both go to the replication log (`Source` and `Operation` on `ue_AIR_IDOReplicationLogs`):

- The **operation** is what the run does with its records at the target: `Insert`, `Update`, `Delete` or `Upsert`. The triggers pass the first three. Anything else the caller passes, blank included, becomes `Upsert` (`NormalizeOperation`), which means insert or update, whichever applies. The operation is also what the target is told (see the target types below), so the log and the target use the same four words. For a `SalesforceRESTAPI` rule, `OperationAtTarget` turns `Insert` and `Update` into `Upsert` before the rule is sent and logged, because Salesforce upserts by external ID either way. The Source still says which event it was. `Delete` is unchanged, and so is every operation of an `AzureEventHub` rule. Rows logged before this keep the operation they had, and the retry task sends them the same way.
- The **source** is what started the run. It is only logged, and a retry leaves it as it was.

| Run | Source | Operation |
| --- | --- | --- |
| The `IdoPostItemInsert` trigger | `Event: After-Insert` | `Insert` (`Upsert` for a Salesforce rule) |
| The `IdoPostItemUpdate` trigger | `Event: After-Update` | `Update` (`Upsert` for a Salesforce rule) |
| The `IdoOnItemDelete` trigger | `Event: Before-Delete` | `Delete` |
| A trigger run that passes none of the three | `Event: Unknown` | `Upsert` |
| A background task run (a bulk load) | `BG Task: Bulk` | `Upsert`, or the operation it passes (`Insert` and `Update` become `Upsert` for a Salesforce rule) |
| The Rules form's Test tab, which passes `Test` as the operation | `BG Task: Test` | `Upsert` |
| A manual resend (`ue_ResendReplications`) | `BG Task: Resend` | `Upsert` |
| A diagnostic trigger (`ue_LogTriggerEvent`, test only) | `Diag: <event>`, or `Diag: Other` | The event's operation, `Upsert` for a collection event, with the Status always `Skipped` |

The values are constants in the Rules ECA (`OperationInsert`, `SourceEventAfterInsert` and so on) and must match the `Operation` and `Source` inline lists on `ue_AIR_IDOReplicationLogs` (columns `operation` and `source`, both required). They are stored as written, with no short codes and no strings.

Every run goes through `RunReplication`, which loads the rules and records, sends them and writes the log. `ue_ReplicateRecordToExternalSystems` calls it once. `ue_ResendReplications(BGTaskNum, ruleNum, fromDate, toDate, scope, queryFilter, recordCap)`, the background task behind the `ue_AIR_IDOReplicationResend` form, calls it once per filter. A resend reloads records from Syteline and sends their current values, never a stored payload. The form has two groups, one per scope:

- **Resend Errors** (scope `Failures`, `ResendFailures`) loads the records that have a `Failed` log row for the rule, by `RowPointer` in batches of 100, with no record cap (see the record cap rule above). The form passes no dates, which takes every failed row. Before it sends, it sets `RetriesRemaining` to 0 on the rows it is about to reload, so the every-minute retry task can't send a stored payload meanwhile. Afterward it marks a failed row `Skipped` when its record was resent or no longer exists, and gives a row its retries back when its record wasn't resent or can't be reloaded (a delete, or a row with no record row pointer), so the retry task resends its stored payload. The group's grid shows the rule's failed rows that the button acts on, plus the ones the retry task still has queued, through a secondary collection (`fds_SC2`, `FILTERPERM(Status = 'Failed' AND RuleNum = FP(RuleNum) AND IDOName = FP(IDOName) AND (Payload IS NOT NULL OR (RecordRowPointer IS NOT NULL AND Operation <> 'Delete')))`), refreshed by the form's `Std…Completed` event handlers. Keep that filter in step with the rows `ResendFailures` selects: the rule's rows for its current IDO that can be reloaded or have a stored payload. A row that can't be reloaded but has a payload and retries left is listed too, although the button leaves it alone, because the retry task is about to resend it.
- **Bulk Resync** (scope `Everything`, `ResendBulk`) runs once, for the records changed in the period that match `queryFilter`, with `recordCap` as the record cap. The period is compared with the rule's `IncrementalWatermarkProperty` (column `incremental_watermark_property`, required, default `RecordDate`), because `RecordDate` doesn't see every change on an IDO with two base tables: `SLCustomers` has `RecordDate` and `AdrRecordDate`. `TryLoadWatermarkProperty` loads it only when a date was given, and stops the task with a message when it isn't a plain property name (it goes into the filter). The IDO's property list (`LoadIDOPropertyDataTypes`) spells the name as the IDO does. A property that isn't listed only gets a warning: as with a field map, the load of the records decides whether it exists. A property whose Mongoose data type is one of the non-date types stops the task (`Date` is the only date type, and a property with no data type is let through with a message), because the dates go into the filter as quoted text and a text property would be compared as text without an error. Nothing else uses the property yet. It doesn't go looking for failed records. A failed row whose record it resent becomes `Skipped`. While it runs, it sets `RetriesRemaining` to 0 on the rule's failed rows that can be reloaded and still have retries, and afterward it puts back the number each one had, so a resync never re-queues an old failure. Like a bulk load, it returns 16 when nothing matched.

A record counts as resent only when the rule got as far as its records. Both dates are optional in both scopes, and a blank date puts no bound on that side of the filters. `recordCap` is a string parameter so the form can pass it blank: blank or 0 means no cap, and a negative number is refused. The form passes the parameters as one comma-separated list (`BGTaskParmsErrors`, `BGTaskParmsBulk`), so a filter with a comma in it doesn't work. The automatic retries are meant to run every minute and cover timing problems, such as a Salesforce child sent before its parent. The resend form is for anything longer.

1. A trigger created by the Config assembly calls `ue_ReplicateRecordToExternalSystems` with the IDO name, a query filter, a record cap, an optional rule number (blank means every active rule) and an optional operation (`Insert`, `Update` or `Delete`; blank, as from background tasks, becomes `Upsert`). It returns early when there are no active rules.
2. `LoadReplicationRulesAndMaps` loads the active rules for that IDO along with their map fields. Each map field has a single source: `Name`, `SourceType` (`IDOProperty` or `Literal`), `SourceValue` and `SourceTransformation` on `ue_AIR_IDOReplicationMapFields`. Replication does not use the `Sources` subcollection or the derived `JSON` property.
3. `LoadSourceRecords` loads the union of each rule's source properties once through `SytelineInternalAPI.LoadRecords`, which wraps `this.Context.Commands`. Data access goes through IDOs, not direct SQL. If the combined load throws, most often because one rule's field map names a property the IDO doesn't have, it loads each rule's records on their own, so only the rule that can't be loaded fails. That rule gets a failed result that names the unknown properties, found with `Context.Commands.GetPropertyInfo`. The property list is only used for the message: a rule fails when its own load fails, never because of the list.
4. For each rule, `RemapRecords` builds the output records from the field map and applies each field's transformation (`ReplicationField.Transformation`). The transformations are defined in `Models/ReplicationFieldTransformTypes.cs`. Each takes the typed value the IDO returns (not a string), nulls stay null, and a value that can't be converted is sent unchanged with a warning (`ReplicationFieldTransform.Convert(value, out warning)`). `RemapRecords` collects the warnings per record, and they reach the record's log row (`ReplicationRecordOutcome.Warning`, appended to `ErrorMessage`). A record with a warning is logged even in runs that only log failures. Date strings are parsed as `DateTimeOffset`, keeping the date as written. Their `Value` strings must match the `SourceTransformation` inline list on `ue_AIR_IDOReplicationMapFields`. The result is sent based on `TargetType`:
   - `AzureEventHub`: `AzureEventHubPusher.Push`, using `CredentialValue01` as the connection string, `CredentialValue02` as the event source and `CredentialValue03` as an optional `MaxBatchKBOverride`. `Option01` is an optional Fabric Event Schema URI, `Option02` is the field used as the record ID in failure messages, and `Option03` (`OperationFieldName`) is an optional body field that receives the operation. Every event also carries the operation (`Upsert` included) as the `operation` user property, which Fabric keeps in event metadata only when the Event Hub source uses **Extended features** (read it with `GETMETADATAPROPERTYVALUE` in a SQL operator). The body field is off by default because Event Schema Eventstreams reject fields their schema doesn't define. When `Option01` is set, each event carries CloudEvents user properties (`type` = schema name, `source`, `dataschema` = the URI), which Fabric Event Schema Eventstreams require. Without it, plain events are sent. The batch size limit depends on the namespace tier (256 KB Basic, 1 MB Standard and up). Batches default to about 220 KB, which is safe for every tier, and `MaxBatchKBOverride` can raise that to at most 850. Only `201 Created` counts as accepted.
   - `LogOnly`: sends nothing, for testing. It waits `Option01` (`DelayMilliseconds`, at most 60,000) to stand in for a slow target, uses `Option02` as the record ID field, and logs every record as `Succeeded`, or `Failed` when `Option03` (`SimulatedResult`) is `Failed`. It needs no credential (a rule's `credential_id` is nullable). Like any target type it is listed in the Credentials and Rules form scripts and in the `TargetType` inline lists on the Credentials, Rules and Logs IDOs.
   - `SalesforceRESTAPI`: `SalesforceRestAPI.UpsertRecords`, using `CredentialValue01` and `02` as the client ID and secret of a Salesforce external client app and `CredentialValue03` as the `Domain`, `Option01` as the sObject, and `Option02` as the external ID field. `Option03` (`DeleteBehavior`) decides what a `Delete` operation does: anything but `Delete` (the default, blank, means `Skip`) skips it, and `Delete` calls `SalesforceRestAPI.DeleteRecords`, which deletes by external ID through the Composite API in batches of 25. A record that's already gone (`NOT_FOUND`, `ENTITY_IS_DELETED`) counts as deleted. Sign-in uses the OAuth client credentials flow only. The username-password flow was removed on purpose, because external client apps don't offer it, so don't add it back. `Domain` works as in SyteBridge and the Bridjer Salesforce library: it is the My Domain name (`mycompany`, or `mycompany--sandboxname.sandbox` for a sandbox), sign-in goes to `https://<Domain>.my.salesforce.com`, and it is required. `NormalizeSalesforceDomain` in the Rules ECA cuts a pasted URL down to the name and rejects anything that isn't a My Domain name. `SalesforceAPICredential` started as a port of Bridjer's, but now carries only `ClientId`, `ClientSecret` and `Domain`.
5. Logging goes through `Utilities.WriteLogMessage`, tied to `BGTaskNum` when the method runs as a background task, and each record's outcome goes to the replication log (`ue_AIR_IDOReplicationLogs`).

A rule's `CredentialValue01`–`10` come from its linked credential record. What each credential value and option means for a target type is defined in two form scripts, which also label and show or hide the form fields:
- the Credentials form's `UpdateValueLabels` (credential keys, each with a flag that says whether the value is sensitive). Each value has two inputs bound to the same property: `ValueNNEdit`, a plain multi-line edit, and `ValueNNMaskedEdit`, a single-line edit with the `ComponentFlags.EDIT_PASSWORD` flag (4), which shows dots. The form designer has no setting for that flag, so it can only be set in the export, and it hasn't been tried on a multi-line edit. On a new record the script shows the plain input for every value. On a saved record it shows the masked one for a sensitive value and the plain one otherwise, and it also shows the `ValueNNPreviewEdit` field beside a sensitive value, bound to a derived `ValueNNPreview` property on `ue_AIR_IDOReplicationCredentials` that returns the first and last 6 characters. When you add a credential value, set its flag.
- the Rules form's `UpdateVariableUI` `config` dictionary (option keys, each with an optional list of choices, as in `Option("DeleteBehavior", Choice("Skip", "..."), Choice("Delete", "..."))`, where a choice is the stored value and a description). Each option has two inputs bound to the same property, `OptionNNEdit` (text box) and `OptionNNCombo` (combobox), because a script can't change a component's type. The script shows the combobox for an option with choices and the text box otherwise. Each combobox's List Source is `INLINE ENTRIES(V(OptionNNChoices)) DISPLAY(1,2) VALUE(1)`, and the script sets the form variable `OptionNNChoices` to the choices for the rule's target type and calls `InvalidateList()` when they change. Filling a combobox with the script's list-box calls (`InsertListBoxString`) doesn't work, and a Script list source runs a global script, not a form script method. A List Source can't be a form variable as a whole either: `V(SomeListSource)` fails at run time with "Unsupported list source format". Only the entries inside `INLINE ENTRIES( )` can come from a variable, so a script-supplied list with no entries still shows as an empty drop-down. The Rules form doesn't show credential values. Its Target tab (`TargetTab`) has one line that shows which credential the rule uses (its ID, name and target type), and the rule's options under it.
- the Rules form's `UpdateSourceValueChoices`, which fills the field map's Source Value drop-down. The `MapFields_SourceValue` grid column's List Source is `INLINE ENTRIES(V(SourceValueChoices)) DISPLAY(1) VALUE(1)`. For a row whose Source Type is `IDOProperty` the script sets `SourceValueChoices` to the property names of the rule's IDO, read with `this.IDOClient.GetPropertyInfo` (the same call replication uses to name an unknown property) and kept per IDO in the form variables `SourcePropertyListIDO` and `SourcePropertyList`. For any other Source Type the list is empty. A lookup that fails isn't kept, so the next call asks again. It runs from `StdObjectSelectCurrentCompleted` on `object2`, from `SetValuesOnNewFieldRecord`, from the Source Type column's Selection event (`MapFieldSourceTypeChanged`), and from the Selection event of both IDO Name components (`RuleIDONameChanged`). A form variable doesn't have to be declared in the export: `ThisForm.Variables(name)` creates it.

- the Rules form's `UpdateIncrementalWatermarkPropertyChoices`, which fills the rule's Incremental Watermark Property drop-down (`IncrementalWatermarkPropertyComboBox`, List Source `INLINE ENTRIES(V(IncrementalWatermarkPropertyChoices)) DISPLAY(1) VALUE(1)`) with the date properties of the rule's IDO. It runs from `StdObjectSelectCurrentCompleted` on `object` and from `RuleIDONameChanged`. It uses the same `GetIDOPropertyEntries` as the Source Value list, with `datesOnly`, which leaves out the properties whose Mongoose data type is a known non-date type, the same rule the Rules ECA's `NonDateDataTypes` applies, so a property with the `Date` data type or with none is listed (kept in the form variable `SourceDatePropertyList`). It falls back to every property when nothing is left. Both lists come from `this.IDOClient.GetPropertyInfo`, not from the `IDOProperties` IDO, because the runtime merges in the properties of an IDO that extends the rule's IDO and `IDOProperties` doesn't show those. Per the DLLs in `Lib/`, `GetPropertyInfo` throws for an IDO name the runtime doesn't know. The script also guards against a response with no `Properties`, which hasn't been seen.

Make the extension class read the same positions the two scripts label. `README.md` documents the same credential values, rule options, transformations and log behavior for administrators, so update its tables, and the matching pages in `wiki/`, when these change.

In a form script, reach the form's primary collection with `this.ThisForm.PrimaryIDOCollection`, not through a grid component's `IDOCollection` or `CurrentIDOCollection`, which is whichever collection happens to be current. It doesn't depend on a component's name, and it is the pattern the owner's other Syteline forms use.

## Diagnostics

Test-only code for finding out how Syteline fires IDO events. It isn't part of replication, and it is kept apart so it can be removed in one piece:

- `Diagnostics.cs` in the Rules ECA (the class is `partial` for it) holds `ue_LogTriggerEvent`, which a diagnostic trigger calls, and `ue_DiagUpdateCollection`, which saves test records through `this.Context.Commands.UpdateCollection`. `ue_LogTriggerEvent` writes one `Skipped` row to the replication log per event, with the Source `Diag: <event>` (the values are in the log's `Source` inline list, so keep the two in step), what the handler passed (`P("RowPointer")`, the IDO's key properties, `P("_ItemId")`) and runtime details (session, machine, thread, `System.Transactions.Transaction.Current`, timings) in the payload. It never throws. `ue_DiagRingDoorbell` (the doorbell test) writes a `Doorbell=<token>` row, submits the `ue_AIR_DiagDoorbellTask` background task through `BGTaskDefinitions.BGTaskSubmit2` (a standard Mongoose method; its 22 parameters are passed by position, and a blank one is added as `Add(null, false)`, because `Add(null)` picks the `Add(InvokeParameter)` overload and adds a null element the runtime throws on), and writes a `DoorbellSubmit=<token>` row with the result. It doesn't submit when `ActiveBGTasks` already lists a doorbell task for the same IDO with the status `READY` and no Start Date (how a queued task shows, as the burst test B3 confirmed; the row lists the statuses and start dates it saw). The task's row lists the doorbell rows it could see, so the burst test can tell whether a save that skipped was picked up. That task runs `ue_DiagDoorbellTask`, which looks for the doorbell row for up to 60 seconds and writes a `DoorbellTask=<token>` row. The three use the Source `Diag: Other`. None of them throws. `ue_DiagTimeLoad` (super users only, read only) loads from an IDO through `this.Context.Commands.LoadCollection` with a chosen `ReadMode` (`Committed`, `Uncommitted` or `Default`) and times each load, for test F3b.
- `SetupDiagnosticTriggers` in the Config ECA creates handlers with the description `ue_AIR_DiagnosticTrigger` for all eight update events on one IDO, plus an asynchronous `IdoPostUpdateCollection`, **created active** and with `IgnoreFailure` set, plus a doorbell handler on `IdoOnUpdateCollection` that calls `ue_DiagRingDoorbell` with `IgnoreFailure` off, as a real doorbell would. On `IdoOnUpdateCollection`, as on `IdoPostItemInsert`, that puts the handler's writes in the save's transaction, and the task submission too ([doorbell results](wiki/Trigger-Diagnostics.md#doorbell-results)). It and `ue_DiagUpdateCollection` (which can delete records) are for super users only (`IDORuntime.Context.SuperUser`), because Execute is granted per IDO, not per method, and both refuse this project's own `ue_AIR_` IDOs (a diagnostic trigger on the log would fire on its own rows without end). `ue_DiagUpdateCollection` also refuses a key prefix shorter than 2 characters or with a LIKE wildcard. Their own description keeps them out of the replication triggers' status, Fix Triggers and Activate All. The key properties come from `GetPropertyInfo` (`PropertyInfo.Key` is the key's position, 0 when it isn't a key).
- `SetupStrictDiagnosticTriggers`, also in the Config ECA, creates the same set as `SetupDiagnosticTriggers` with Ignore Failure off on every handler, no asynchronous handler, and the doorbell on `IdoPostUpdateCollection` (`-Strict` in the test script), for [the last tests before building](wiki/Trigger-Diagnostics.md#the-last-tests-before-building). `RemoveDiagnosticTriggers` removes either set.
- `wiki/Trigger-Diagnostics.md` is the test plan: each test, the assumption it answers, and what the DLLs predict.

To add a new target type:
- add a `case` in that `switch`
- add a helper, plus models under the target's own folder, in both projects
- add its credential keys to the Credentials form script and its option keys to the Rules form script

## Building

You need Windows with Visual Studio/MSBuild and the .NET Framework 4.8 targeting pack, and you have to restore NuGet packages first. The .NET SDK and MSBuild aren't available in this Linux container, so you can't compile changes here. The Build workflow (below) compiles them on the pull request. Build each solution on its own, for example:

```
nuget restore "src/IDO Extension Class Custom Assemblies/ue_AIR_IDOReplicationRules_ECA/ue_AIR_IDOReplicationRules_ECA.sln"
msbuild "src/IDO Extension Class Custom Assemblies/ue_AIR_IDOReplicationRules_ECA/ue_AIR_IDOReplicationRules_ECA.sln" /p:Configuration=Release
```

`.github/workflows/build.yml` does this build for both solutions on every pull request and every push to `main`, on a Windows runner, and publishes the two DLLs as artifacts of the run (kept 14 days). The same workflow runs `.github/scripts/compare-shared-code.sh`, which fails when `Helpers/` or `Models/` differ between the two projects by more than the project name. That script runs here too, so run it after changing a helper or model. A third job, **Form scripts compile**, extracts each form's script from its FormSync export (`.github/scripts/extract-form-scripts.py <folder>`, which also runs here) and compiles it against `Lib/` with C# 7.3. Syteline compiles a form's script when the form opens, and one compile error stops every script on that form, so read this job's result after editing a `<ScriptLine>`. A green build only proves the code compiles; nothing is run against Syteline. After pushing, read the Build result on the pull request, and fix a failure before calling the change done.

Upload the built DLL to Syteline (IDO Extension Class Assemblies). Then re-export the IDOs to refresh `dist/`, which picks up the new assembly image and any method signature changes. `bin/` and `obj/` are gitignored, so don't commit build output.

An IDO method's name in the IDO must exactly match the C# method name, `ue_` prefix included. That applies to strings that reference a method, like the `METHOD("...")` in trigger `EventActions`.

## Pull requests

After pushing changes to a branch, always open a pull request against `main` without asking first. If the branch already has an open pull request, the push updates it.

### Review your own change before every push

Before every push, have the change reviewed by a separate agent that hasn't seen your reasoning. That covers the push that opens a pull request and each later push to it. The Claude Code Review check that runs on each pull request keeps finding real bugs in first passes, and finding them first saves a round trip.

This applies to every change: C#, the IDO and form exports, the SQL files, and documentation on its own. One review per push is enough. Small fixes you make because of the review don't need a second review.

1. **Commit the change, then run `git fetch origin main`.** The reviewer reads what the branch adds over `main`. Have it start with `git diff --stat origin/main...HEAD` and then read `git diff -I'^[A-Za-z0-9+/=]{60,}$' origin/main...HEAD`. The `-I` option leaves out the base64 lines of the two assemblies embedded in the IDO export. A re-export rewrites about 4,000 of those lines, and without it they bury the changes that matter. On a later push, also tell the reviewer which commits are new since the last push.
2. **Start a subagent as the reviewer.** Tell it to report findings and not to edit files. Give it the diff command, the repository path and what the change is meant to do. Don't give it your conclusions or tell it the change is correct. If the session has a code review skill, you can run it as well, but it doesn't replace the subagent, because the subagent is the one that gets the checklist below.
3. **Give it this checklist.** Ask it to look for:
   - an assumption about Mongoose or Syteline that isn't verified in the code or in the section "Mongoose facts that are easy to get wrong" in this file
   - a path where a failure loses data, a log row or a retry
   - a path that can throw out of a trigger
   - a helper or model changed in one project and not the other
   - a schema, IDO or form change that `wiki/Installation.md` (its install steps and its Upgrading section) and the README's install steps don't mention
   - documentation that says something the code doesn't do
   - a rule in this file that the change breaks, for example a hand-edited IDO without its revision bumped, two places that must hold the same string and no longer do, or an `<AssemblyImage>` edited by hand (a re-export that replaces the whole image is normal)
4. **Check each finding against the code.** Fix the ones that are real. Nothing runs locally, so some findings can't be confirmed either way. Don't change code for those, and don't drop them: list them as unverified.
5. **Put a "Self-review" note in the pull request description.** Say what the review found, what you changed, and what is left unverified. If it found nothing, say that. Update the note on each later push.

The Claude Code Review check still runs afterward. Treat it as the second check, not the first.
